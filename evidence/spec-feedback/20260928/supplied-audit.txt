Part 4 — Grading "What We Pay Attention To"

1. The spec could replace the code: 2/5.
- For: spec.md cleanly separates D-sentences, a rule table with precedence, replay tables and an input contract, and three of my five mutations produced named, line-cited refusals.
- Against: the engineer is expected to own 2,389 lines, about 930 of which are JSON schema. The rule language can't express force majeure or criticality. A fresh agent facing one new status value opened 5 source files because the spec and package don't expose the status enum or the refusal-retention behavior.
- Most limiting: #18.

2. Checks derived from the spec rather than hand-written: 3/5.
- Genuinely derived: the rule and precedence tables produce the consequences and replay expectations. Behavior-level teeth are real: the routine→candidate change turns Gates 1 and 2 red.
- Hand-written: 23 hand-authored D-check classes cover 41 of 73 sentences; 32 sentences have no check at all. They are bound to sentences by hashes a writer can re-point unseen, and the check logic doesn't read the sentence's quantifier.
- Most limiting: #1.

3. How much it finds from evidence, and how openly the gap is described: 3/5.
- For: it finds 11 lifecycle failures in the inherited system and states UNKNOWN honestly throughout.
- Against: the top-level surface omits those findings and the inherited false positives. The SIGNAL-003 PASS rests on synthetic fixtures while the declared FM case errored. The "critical" metric has no discriminating power.
- Most limiting: #10.

4. Fresh-session recovery and learning that persists: 3/5.
- For: my headless session needed no human explanation, verified the hashes, respected pending-vs-approved, found a real D5 violation, and left a proposal that the next context selection picks up as unapproved.
- Against: it needed 5 source reads. The recorded exercise is scripted, predates four code commits, and made no change.
- Most limiting: #15.

5. Sense of which findings matter reflects trading-desk risk: 2/5.
- Where the effort went: most of it is governance machinery: receipts, detached name bindings, historical-identity preservation.
- What's missing on trading risk: the FM notice erroring in one capture never appears as a missed critical disruption. The inherited-vs-rebuilt recall and false-positive trade is never stated. The flagship open-risk proposal would remove every true negative in the corpus because Critical=1 everywhere.
- Most limiting: #12.

6. Working through disagreement: 3/5.
- For: the response to the previous audit is exemplary in form. The audit is kept verbatim, each finding has a disposition, and the failed first proof attempt is kept rather than hidden.
- Against: every point was accepted and patched at exactly the probe that was used. Nothing was held and argued; for example, whether Gate 3 should exist at all was never defended or dropped.
- Most limiting: #25.

❯ what would make the spec go from a 2 to a 5

⏺ The test for a 5 is behavioral: a fresh agent handles an unanticipated change with zero source reads, and every sentence the engineer edits either changes what the harness does or is marked as unchecked. Today's spec fails that in three ways. Each fix below comes from something I observed in the audit.

  Getting to 3: make it say everything the implementation decides

  The WITHDRAWN session opened 5 source files because two facts that govern behavior were only in code.

  - Status vocabulary and chain semantics. The spec buries the INITIATE/SUPERSEDE/TERMINATE enum in JSON, and the package excerpt dropped it. Put every closed value set the rules test into a short table, including what happens to a value outside the set. Today that answer is "exit 2, nothing retained", and it's written down nowhere.
  - Where refusals are produced. D5-001 says refused input is retained. The publisher raises an exception and the harness wrapper fills in the disposition. The spec needs a component-boundary rule, e.g. "the component, not the caller, emits the refusal decision and retains it", with a replay row that calls the component directly.
  - Criticality and force majeure. The brief's first strong-signal attribute has no rule column. Add a Notice type column (FORCE MAJEURE / other). Don't key on the Critical header: it is 1 on all 14 labeled notices.

  Getting to 4: remove everything the engineer can't act on

  About 60% of the file is currently noise to its owner.

About 60% of the file is currently noise to its owner.

- Remove implementation status. "Implementation status", "Check status", "Demonstrated evidence" and "Validation: Gate 1 / deferred" appear on every requirement. They already disagree with coverage (INPUT-002 says not_available here, PASS 9 there). Generate them into coverage only.
- Remove the interface JSON schemas (about 930 lines). Keep them as generated artifacts referenced by hash. The engineer owns the table that produces them, not the schema.
- Remove the history. That covers the historical promotion boundary, "policy version 2" assumptions, ADR provenance and the timezone-evidence narrative. Keep one line per active decision. Fix ARCH-SOURCE-001, which says "keep TZ-NGPL-001 pending" while the next row says rejected.
- Delete the dead columns. Arriving status, Prior and Source clock are ANY in every rule. A column no rule uses teaches the reader nothing.
- Rewrite SIGNAL-003 as a rule, not a test case. "Detect the labeled force-majeure disruption, ids [46864]" is a test fixture. Move 46864 to the regression table.

Target: under 600 lines, readable in 30 minutes, with every paragraph either normative or deleted.

Getting to 5: make the prose itself executable, or visibly unchecked

This is the gap behind finding #1 (the hash rebind that turned PASS on the opposite sentence).

- Parameters in the spec, not the checker. D1-005's "at most one" lives inside a hand-written check called one_initial. Put quantities and quantifiers in a table the check reads (max_initial_alerts_per_event: 1). Then editing the sentence is editing the behavior, and the hash-binding mechanism can go.
- Mark every D-sentence as one of two kinds. It is either expressed in a table (rules, replays, parameters) or explicitly UNCHECKED with its reason. Today 32 of 73 sentences are silently UNKNOWN. The engineer should see them as a short, owned list.
- Consequences on proposals, not just commits. The critical amendment would have removed all 6 true negatives, and nobody ran it. A spec at 5 lets the owner run make consequences on a proposed edit and see which labeled notices flip before approving.
- Decisions that name a person and a desk rationale in the spec. Every row currently has Person: PENDING_PERSON. If the spec is the owned artifact, ownership should be visible in it, not in a detached JSON file.

How to prove it's a 5

Do the audit again, with the owner hands-off:

1. Fresh agent. Run README's first message with the WITHDRAWN change (or any status or format the spec lacks). Pass condition: zero reads of rebuilt/ or harness/. The agent either implements it after an approved spec edit or stops with questions that cite spec rows only.
2. Random mutations by someone else. Mutate 10 random rows or parameters across the rules, replays, parameters and input tables. Each one must produce a named, line-cited change in gate output or consequences. None may be absorbable by editing a file outside spec.md.
3. Engineer comprehension. An engineer who didn't write it, given only spec.md, predicts the disposition for 5 unseen notices and matches the harness.

If all three hold, the spec has replaced the code. At a quarter of the current length, it would also score better on parsimony.
